# FAQ 유사 표현 유형 검증 명세

- 작성일: 2026-10-28
- 상태: 구현 전 제안 명세
- 확인 기준: 로컬 `BreathAI-deployment` 소스. 운영 실행의 원본 LLM 응답 및 프런트엔드 구현은 미확인.
- 범위: FAQ 후보의 `synonyms[].type` 생성·검증·저장·표시. 이 문서는 코드 변경이나 운영 데이터 변경을 수행하지 않는다.

## 1. 목적과 데이터의 의미

`TYPO`는 FAQ 후보에 연결된 유사 표현에 실제 철자·자모·띄어쓰기 오류가 있다는 뜻으로 한정한다. 미답변 원본 로그의 오류 여부나 미답변 발생 원인을 의미하지 않는다.

현재 흐름은 `미답변 로그 → 군집 → LLM의 FAQ 및 유사 표현 생성 → 형식 검증 → 콜백 → 백엔드 저장 → 조회`이다. 유사 표현은 원본 로그와 같을 수도 있지만, 원본에서 관측됐다는 보장이 없는 생성 결과다. 이 라벨로 ‘오타로 인한 미답변 건수’를 집계해서는 안 된다.

## 2. 현재 코드와 문제

| 위치 | 현재 동작 | 문제 |
| --- | --- | --- |
| `services/faq_generator.py`의 `PROMPT_TEMPLATE` | 유사 표현 10개와 TYPO/ABBR/SYNONYM 생성 요청 | 오류의 정의, 정상 표현의 반례, 판정 근거가 없다. 정확히 10개라는 요구는 불필요한 변형 생성 압력을 줄 수 있으나, 이번 오분류의 직접 원인으로 입증된 것은 아니다. |
| 같은 파일의 `validate()` | 타입이 세 enum 중 하나면 수용 | 정상 문장에 붙인 TYPO도 통과한다. 잘못된 타입은 SYNONYM으로 바뀌어 분류 실패가 숨겨진다. |
| `services/callback_payload.py` | text의 문자열 여부와 enum만 검사 | 의미 검증이나 검증 이력 확인이 없다. |
| `DashboardService.java` | 전달받은 타입을 enum으로 저장 | AI의 잠정 판단과 검증된 판단을 구분하지 않는다. |
| `SynonymCandidate.java` | text/type 저장 | 교정 대상, 판정 근거, 원문 관측 여부, 정책 버전이 없다. |
| `services/answer_evaluator.py` | 답변 품질 평가 | 유사 표현의 유형 정확성을 검증하는 단계가 아니다. |

예를 들어 `와이파이 비밀번호는?`를 TYPO로 입력하면 현재 `validate()`는 그대로 반환한다. 맞춤법을 판정하는 코드가 잘못 동작한다기보다, 모델의 분류를 검증하는 단계 자체가 없는 구조다.

또한 ‘모든 출력은 자연스러운 한국어’라는 지시와 실제 오류형 표현 생성의 관계가 불명확하다. 표준 질문·답변은 정상 문장으로, 유사 표현의 오류형은 관측 근거가 있을 때만 보존하도록 구분해야 한다.

## 3. 분류 기준

| 유형 | 판정 조건 | 해당하지 않는 경우 |
| --- | --- | --- |
| `TYPO` | 표현 내부에 구체적으로 지목 가능한 오류가 있고, 의미를 유지하는 최소 교정형과 검증 근거가 있다 | 표준 질문과 문장이 다름, 짧음, 조사·어미 변화, 물음표, 외래어의 한글 표기 |
| `ABBR` | 정상적인 축약 표현이 있으며 그 확장형을 제시할 수 있다 | 단순한 문장 생략이나 짧은 질문 전체 |
| `SYNONYM` | 같은 FAQ 의도에 대응하는 정상 동의어·유사 질문·문장 변형 | 의도가 다르거나 의미를 확정할 수 없는 표현 |

복수 특성이 있으면 검증된 오류가 있는 경우 TYPO, 오류가 없고 명시적인 약어가 있으면 ABBR, 나머지 정상 변형은 SYNONYM으로 정한다. 불확실한 오류를 TYPO로 확정하지 않는다.

예시:

| 표현 | 기대 유형/처리 | 이유 |
| --- | --- | --- |
| 무료 와이파이는? | SYNONYM | 정상 질문의 축약 |
| 와이파이 비밀번호는? | SYNONYM | 정상 질문 |
| 와이파이 비번 | ABBR | 비번 → 비밀번호 |
| WiFi | ABBR | 해당 FAQ 문맥에서 와이파이의 통용 표기/약칭으로 허용하는 명시적 정책 적용 |
| 와이파이 | SYNONYM | 정상 외래어 표기 |
| 와이파이 비밀번허 | TYPO | 비밀번허 → 비밀번호. 승인된 오류·교정 쌍이 있는 경우 |
| 와이파이비밀번호 | TYPO 또는 검토 보류 | 승인된 띄어쓰기 규칙이 있으면 TYPO. 공백 차이만으로 자동 확정하지 않음 |
| 널리 쓰이는 신조어·상품명·역명 | 보호 또는 검토 보류 | 사전 미등재만으로 오류 판정 금지 |
| 다른 FAQ 의도의 표현 | 제외 또는 검토 보류 | 유형 분류 이전에 의도 적합성을 확인해야 함 |

영문·외래어라는 이유만으로 TYPO를 부여하지 않는다. WiFi 등의 표기 정책은 별칭 목록으로 명시하며 일반 영단어 전체에 확대 적용하지 않는다.

## 4. 목표 처리 흐름

1. LLM은 FAQ와 유사 표현 후보를 최대 10개 제안한다. 수량을 맞추기 위한 인위적 오타 생성은 금지한다. 초기 버전의 TYPO 후보는 해당 군집의 실제 입력에 관측된 표현으로 제한한다.
2. 입력 품질을 검사한다. 비문자열·빈 문자열·100자 초과는 제외하거나 검토로 보낸다. 100자는 현재 DB의 text 길이 제약 기준이며 임의 절단하지 않는다.
3. 원문은 보존하고 NFC와 양끝 공백 정리 등으로 별도 비교 키를 만든다. 같은 후보 내부의 중복을 제거한다. 오류 검증 전에 내부 공백이나 철자를 교정해서 증거를 없애지 않는다.
4. 같은 FAQ 의도의 표현인지 검증한다. 명백한 불일치는 제외하고 애매한 표현은 검토 보류한다. 이 단계의 모델 판정도 사실 보장으로 취급하지 않는다.
5. TYPO 제안에는 오류 구간·교정형·관측 출처를 요구한다. 확장형이 있는 정상 약어는 ABBR로, 정상 문장 변형은 SYNONYM으로 재분류한다.
6. 승인된 오류·교정 사전 및 제한된 결정적 규칙으로 확인되는 경우에만 TYPO를 확정한다. LLM의 자기 설명이나 문자열 편집 거리만으로 확정하지 않는다. 초기 규칙으로 확인할 수 없는 실제 오류도 검토 보류할 수 있다.
7. 확정된 표현만 기존 콜백의 `synonyms[{text,type}]`에 포함한다. 보류 결과는 별도 검토 산출물에 남긴다. 특정 표현의 보류 때문에 FAQ 전체 분석을 실패시키지 않는다.
8. 콜백 전 검증 정책 버전과 검증 산출물의 일치 여부를 확인한다. 검증 산출물 누락은 새 정책 작업에서 정상 완료로 처리하지 않는다. 기존 작업 호환 경로는 명시적으로 구분한다.

TYPO 근거가 부족하다는 이유만으로 SYNONYM으로 바꾸지 않는다. 정상 유사 표현임을 확인한 경우에만 변경하고, 그 외에는 보류한다. 잘못된 enum도 SYNONYM 기본값으로 숨기지 않는다.

## 5. 내부 검증 데이터 계약

외부 콜백은 초기 구현에서 유지하고, AI 작업별 내부 산출물 `synonym_validation.json`을 추가하는 방안을 제안한다. 미확인 필드를 기존 API에 바로 전달하지 않는다.

검증 기록에는 다음 정보가 필요하다.

| 필드 | 의미 |
| --- | --- |
| `clusterLabel`, `candidateText` | 작업 내 후보 연결 키 |
| `proposedType`, `finalType` | 모델 제안과 검증 후 유형. 보류/제외 시 finalType은 null |
| `status` | ACCEPTED / RECLASSIFIED / REVIEW_REQUIRED / DROPPED |
| `correctedText`, `errorSpan` | TYPO의 최소 교정형과 오류 구간. 다른 유형은 null |
| `expandedText` | ABBR의 확장형 |
| `sourceKind`, `sourceLogIds` | OBSERVED / GENERATED, 작업 내 원본 로그 ID. 생성 표현은 ID 없음 |
| `ruleId`, `reasonCode`, `policyVersion` | 판정 규칙과 사유, 재현에 필요한 버전 |

`sourceLogIds`는 업로드 내 식별자이며 DB 기본키로 간주하지 않는다. 원문에서 관측됐다는 사실은 오타라는 증거가 아니므로 별도 검증한다. 생성 표현을 OBSERVED로 표시해서도 안 된다.

오류 구간은 원문 NFC 기준의 문자열 시작 위치와 끝 위치(끝 제외)로 정의한다. 교정형이 원문과 같거나, 오류 구간이 원문 범위를 벗어나거나, 사전/규칙의 교정형과 불일치하면 TYPO 확정을 거부한다. 문장 전체를 표준 질문으로 바꾸는 것은 최소 교정으로 인정하지 않는다.

## 6. UI·백엔드 및 기존 데이터

- 최초 적용은 외부 enum과 DB 스키마를 유지한다. 검증된 최종 유형을 기존 컬럼에 저장한다.
- UI의 영역명은 ‘유사 표현’으로 하고, 유형 설명에 ‘FAQ에 연결된 표현의 유형이며 미답변 원인 분석 결과가 아님’을 명시한다. 구체적인 UI 수정 위치는 프런트엔드 확인 후 정한다.
- 운영자 검토 화면에서 근거·교정형·보류 상태를 보여 주려면 후속 API/DB 확장이 필요하다. 내부 JSON만으로 이 화면이 구현되는 것은 아니다.
- 기존 TYPO를 일괄 SYNONYM으로 바꾸지 않는다. 승인 전 후보부터 읽기 전용 재검증 보고서를 만든다. 기존/제안 유형, 사유, 변경 대상을 비교할 수 있어야 한다.
- 기존 데이터에 출처나 근거가 없으면 이를 추정해 채우지 않는다. LEGACY_NO_EVIDENCE 사유로 보류할 수 있다.
- 이미 승인되거나 배포된 FAQ 연결 표현은 자동 재작성하지 않는다. 변경안 검토 후 별도 적용하며, 이전 유형·정책 버전을 기록해 롤백 가능하게 한다.
- 유형 변경은 원본 미답변 로그나 미답변 통계를 변경하지 않는다.

## 7. 구현 범위와 순서

1. 독립적인 유사 표현 검증 모듈과 정책 파일을 추가한다. 모델 호출 없이 정책 검증을 실행할 수 있어야 한다.
2. FAQ 프롬프트를 수정한다. 최대 개수, 정상 표현 반례, 관측된 오류형만 허용, 잠정 유형/근거 제출을 명시한다.
3. `faq_generator.validate()`를 형식 검증과 의미/정책 검증으로 분리하고, 원본 군집 샘플과 ID를 검증기에 전달한다.
4. 작업별 검증 산출물을 저장하고 `callback_payload.py`에서 확정 결과만 전송하도록 연결한다. 모든 유사 표현이 보류되면 빈 배열을 허용한다.
5. 오프라인 회귀 검증 후, 운영 데이터 변경 없이 기존 결과와 새 결과를 비교하는 시범 실행을 한다.
6. 적용 대상을 검토한 뒤 신규 작업부터 정책을 활성화한다. 과거 데이터 재처리는 별도 실행으로 분리한다.

## 8. 검증 및 수용 기준

- 위 표의 정상 와이파이 표현은 TYPO로 확정되지 않아야 한다. `비번`은 ABBR로 처리해야 한다.
- 승인된 오류·교정 쌍은 TYPO로 유지되고 원문과 교정형을 함께 추적할 수 있어야 한다.
- 물음표, 문장 생략, 어미 차이, 영문 표기만으로 TYPO를 부여하는 회귀가 없어야 한다.
- 사전 미등재어·불확실한 교정·잘못된 enum은 정해진 보류/제외 사유를 남겨야 한다.
- 빈 값, 비문자열, 길이 초과, 중복, 여러 유형이 혼재한 입력을 검증해야 한다.
- 검증 전후 콜백과 백엔드 저장/조회 연계를 확인한다. 검증 실패 항목이 확정 TYPO로 저장되면 실패다.
- 사람 검수 데이터에서 TYPO 정밀도, 실제 오류 재현율, 유형별 오분류, 보류율, FAQ당 확정 표현 수를 비교한다. 생성 결과와 원본 로그는 별도 모집단으로 집계한다.
- 초기 출시 조건은 필수 회귀 사례 전부 통과 및 검수 세트에서 기존 대비 TYPO 오탐 감소다. 전체 정확도 수치는 검수 세트 구성과 함께 보고하며 사전에 임의 수치를 성능 보장으로 제시하지 않는다.
- 산출물과 정책이 같으면 검증 결과가 같아야 한다. 모델 생성 자체의 재현성은 별도 관리한다.

## 9. 별도 이슈: 급증 키워드의 동사 활용형

두 번째 이미지의 `넣고/넣나요/넣으면`은 TYPO 라벨 경로가 아니다. `keyword_policy.py`가 한글 2글자 이상을 정규식으로 추출하고 불용어와 정확히 일치하는 항목만 제거하며, `dashboard_metrics.py`가 키워드 출현을 집계한다.

이 문제는 키워드 품사 선별·기본형 통합·불용어 정책의 별도 명세로 다룬다. 모든 동사 제거는 `환승하다` 등 의미 있는 행동 표현까지 제거할 수 있으므로 이번 TYPO 수정에 묶어 일괄 적용하지 않는다.
